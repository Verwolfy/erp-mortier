# PLAN DE RECONSTRUCTION COMPLÈTE — ERP Mortier, Adjuvants & Peinture

**Statut :** document de référence unique et figé (source de vérité). Toute reconstruction, avec Gemini ou tout autre assistant, doit s'appuyer exclusivement sur les noms exacts définis ici — fichiers, onglets, colonnes, préfixes d'identifiants, listes de choix. **Aucun nom ne doit être inventé, renommé ou "amélioré" en cours de route.** C'est précisément l'absence d'un tel document qui a causé les incohérences de nommage observées précédemment.

---

## 0. Pourquoi ce document et comment l'utiliser

Le problème rencontré (Gemini renommant les onglets différemment à chaque échange, perdant la liaison entre le code et les Google Sheets réels) vient d'un manque de **document de référence unique, figé, consulté à chaque étape** — les noms étaient réinventés à la volée à partir de la mémoire de la conversation, qui dérive avec le temps.

**Règle d'usage :** ce document devient le fichier `docs/schema_reference.md` du repo GitHub, à référencer explicitement dans chaque prompt Gemini ("respecte exactement les noms d'onglets et de colonnes définis dans `docs/schema_reference.md`, ne les modifie jamais sans confirmation explicite de ma part"). Il remplace et unifie tous les échanges précédents.

**Recommandation forte :** recréer des fichiers Google Sheets neufs (nouveaux ID) plutôt que de réutiliser les fichiers existants dont la structure a dérivé — plus sûr que de nettoyer/renommer des onglets existants en conservant un risque de résidus incohérents.

## 1. Architecture globale (rappel)

```
┌────────────────────────────────────────────────────────────┐
│                   STREAMLIT APP (Streamlit Cloud)            │
│  app.py (routage) → modules/<nom>/{views.py, service.py}    │
│  → core/sheets_service.py (accès Sheets centralisé + cache   │
│    + retry + écritures groupées + verrouillage optimiste)    │
└──────────────────────────┬───────────────────────────────────┘
                            │ Google Sheets API
                            ▼
┌────────────────────────────────────────────────────────────┐
│         8 FICHIERS GOOGLE SHEETS (détail en §2)               │
│  ERP_Referentiels · ERP_Achats · ERP_Stocks · ERP_Production  │
│  ERP_Ventes · ERP_Crm · ERP_Rh · ERP_Logs                     │
└────────────────────────────────────────────────────────────┘
```

**Convention de nommage figée, sans exception :**
- **Noms d'onglets** : `PascalCase`, sans underscore, sans accent (ex. `MatieresPremieres`, pas `Matieres_Premieres` ni `MatièresPremières`).
- **Noms de colonnes** : `snake_case`, sans accent, tout en minuscules (ex. `stock_mini`, pas `Stock_Mini` ni `stockMini`).
- **Noms de fichiers Google Sheets** : `ERP_<Domaine>` (ex. `ERP_Referentiels`).
- **Modules de code** : `modules/<nom_minuscule>/` correspond exactement au `module_name` utilisé dans `core/sheets_service.py` pour retrouver l'ID du fichier (voir `config/settings.py::SHEETS_IDS`).

## 3. Listes de référence et choix automatisés (menus déroulants)

### 3.1 Mécanisme technique

Une **seule** table `ListesReference` (dans `ERP_Referentiels`, voir §2.1) pilote tous les menus déroulants de l'application, plutôt que des onglets séparés par liste (plus efficace en lecture : une seule requête peuple tous les menus). Structure :

```
liste_code | parent_code       | valeur_code | valeur_libelle           | ordre | actif
PAYS       | (vide)            | DZ          | Algérie                  | 1     | OUI
WILAYA     | PAYS:DZ           | 16          | Alger                    | 16    | OUI
CAT_CLIENT | (vide)            | PRO_BTP     | Professionnel BTP        | 1     | OUI
```

**Fonction centrale unique** dans `core/sheets_service.py` (ou un nouveau `core/listes_service.py`) :
```python
def get_liste(liste_code: str, parent_value: str = None) -> list[dict]:
    """Retourne les valeurs actives d'une liste, filtrées par parent si fourni."""
```
Utilisée partout où un `st.selectbox` doit proposer un choix contrôlé plutôt qu'un champ de texte libre. Le cascading (ex. Pays → Wilaya) se fait via `parent_code = f"PAYS:{code_pays_selectionne}"`.

**Pourquoi une seule table plutôt qu'un onglet par liste :** moins d'appels API (une lecture couvre toutes les listes, mise en cache une seule fois), plus simple à faire évoluer (ajouter une valeur = ajouter une ligne, pas créer un nouvel onglet), et cohérent avec la contrainte de quota Google déjà documentée.

⚠️ **Important :** ces codes SH à 6 chiffres sont la norme internationale et fiables tels quels. Utiliser ces codes à 6 chiffres comme base de la liste `HS_CODE`, et prévoir une colonne `sous_position_algerienne` à compléter avec votre transitaire plutôt que de laisser Gemini deviner les chiffres manquants.

## 5. Gouvernance des identifiants (règle anti-duplication, définitive)

Pour éviter la récurrence du bug d'identifiants dupliqués déjà rencontré, chaque entité est classée dans l'une des deux catégories suivantes, **sans exception ni improvisation** :

| Catégorie | Génération | Entités concernées |
|---|---|---|
| **Séquentiel lisible** (`generate_unique_id`, lit les ID existants) | `PREFIXE-0001`, incrémental | Fournisseurs (`FRN`), MatieresPremieres (`MP`), Produits (`PF`), Sku (`SKU`), Clients (`CLI`), Contrats (`CTR`), Users (`USR`), CommandesAchats (`CMA`), AppelsOffres (`AO`), BonsReception (`BR`), Recettes (`REC`), OrdresFabrication (`OF`), Devis (`DEV`), CommandesVentes (`CDV`), BonsLivraison (`BL`), Employes (`EMP`), Projets (`PRJ`) |
| **Technique uuid** (`generate_technical_id`, pas de lecture préalable) | `PREFIXE-` + `uuid4().hex[:10]` | LignesAchats, ReponsesAppelsOffres, Mouvements/MouvementsPf, Lots, LignesRecette, ControleQualite, LignesDevis, LignesCommandeVentes, LignesFacture, Reglements/ReglementsFournisseurs, Interactions, DemandesConges, Taches, FeuillesDeTemps |
| **Séquentiel légal avec compteur atomique** (`Compteurs`, verrouillage optimiste obligatoire) | `FAC-AAAA-000001` | Factures (numérotation sans trou, obligation légale) |
